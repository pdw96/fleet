01

요약 — 왜 v2 인가

v1(풀 클라우드)은 "남에게 파는 멀티테넌트 SaaS" 를 전제로 K8s + microVM 플릿을 설계했다. 그 설계의 비용 지배 항은 샌드박스-초(실행 컴퓨트)였고, 최대 제약은 구독 OAuth ToS(제3자 서버에서 사용자 구독 실행 금지)였다. v2 는 전제를 바꾼다 — 1차 목표는 "내가 어디서든 브라우저로 쓰는 Fleet" 이다. 그러면 두 문제가 동시에 풀린다:

  • 실행이 내 PC 로 내려온다 → 샌드박스 컴퓨트 비용 소멸, 클라우드에는 무료 티어로 충분한 관제탑만 남는다.
  • 실행이 본인 머신이다 → 구독 CLI(Claude Pro 등)를 데스크톱 Fleet 과 같은 위치에서 쓸 여지가 생긴다(§10, 회색지대 유의).
  • 단일 사용자다 → microVM 급 격리가 불필요해지고 평범한 Docker 컨테이너로 충분하다.

프론트엔드 자체 호스팅 웹 Vercel — 기존 React renderer 이식
연결 러너 심 gRPC (클라우드 내부) 아웃바운드 전용 — 러너가 Supabase 에 접속해 작업을 당김(pull). 포트포워딩 불필요

버려지는 것이 없다. Supabase 는 Postgres + RLS 이므로 v1 의 멀티테넌시 데이터 설계가 그대로 유효하고, 코어 엔진의 포트/어댑터 구조도 동일하게 쓰인다. 나중에 상용 SaaS 로 가면 러너만 클라우드 microVM 플릿으로 갈아끼우면 된다(§11).

워크스페이스

로컬 디스크 바인드 마운트 (데스크톱과 동일) — 옵션: git 체크아웃 모드

런 시작: 브라우저가 runs 테이블에 행 삽입 → 러너가 Realtime 으로 감지 → 실행 → 진행 상황이 역방향으로 흐름

왜 오케스트레이터가 PC 쪽인가. Supabase 의 서버 코드 실행 수단(Edge Functions)은 수초짜리 단명 함수라 몇 시간짜리 오케스트레이션 루프를 수용할 수 없다. 코어 엔진을 러너에 두면 클라우드에 새로 짤 백엔드가 사실상 사라지고, CLI 스폰·verify 실행과 같은 프로세스에 있어 데스크톱과 코드 경로가 동일해진다 — 이식 리스크 최소화.

04

러너 설계 — 내 PC 의 Docker

러너는 docker compose up -d 하나로 뜨는 상주 데몬이다. 부팅 시 Supabase 에 로그인하고, Realtime Presence 로 "러너 온라인" 을 알리며, runs 테이블 구독을 걸어둔다.

런 1회의 수명주기 (pull 모델)

1 · 요청

브라우저: runs 에 행 삽입 (status=queued)
→

2 · 감지

러너: Realtime 알림 → 행을 원자적으로 claim (status=running)
→

3 · 실행

코어 엔진 루프 — CLI 컨테이너 스폰 · verify · 승인 요청은 §7 큐로
→

4 · 중계

토큰 → Broadcast · 상태/이벤트 → Postgres
→

5 · 완료

status=done/failed · 산출물 링크 기록 · 컨테이너 정리

claim 은 UPDATE ... WHERE status='queued' RETURNING 으로 원자화 — 러너를 나중에 2대 이상 등록해도 중복 실행이 없다

  • 구성 — ① 러너 데몬 컨테이너(코어 엔진 + supabase-js), ② CLI 이미지(claude/codex/gemini + node/git/verify 툴체인), ③ 워크스페이스 바인드 마운트. 구독 CLI 를 쓸 경우 로그인 상태 디렉터리(~/.claude 등)를 볼륨으로 유지.
  • 연결 회복 — WebSocket 이 끊기면 지수 백오프로 재접속, 복귀 시 queued 행을 폴링으로 1회 보정(이벤트 유실 대비). 하트비트를 runners 테이블에 주기 기록해 브라우저가 "러너 오프라인" 을 표시.
  • PC 절전/종료 — 러너가 죽으면 running 행이 고아가 된다 → 하트비트 만료 시 status=stale 로 전환하고 재시작 시 재개(코어의 CLI 세션 resume 활용) 또는 실패 처리.
  • Windows 전제 — Docker Desktop(WSL2 백엔드). 바인드 마운트는 WSL2 파일시스템 쪽에 워크스페이스를 두는 편이 I/O 성능상 유리.
  • 업데이트 — 러너 이미지는 태그 고정 + watchtower 류 자동 갱신은 쓰지 않는다(실행 중 런 보호). 수동 compose pull.
05

데이터 모델 — Supabase Postgres

데스크톱의 StoreState 를 테이블로 전개한다. 모든 행에 owner_id(auth.users 참조)를 두고 RLS 로 "본인 것만" 을 강제 — 지금은 단일 사용자지만, 이 한 줄이 나중에 팀/멀티테넌트 확장의 기반이 된다(owner_id → org_id 승격).

테이블 내용 비고
projects 프로젝트 · 워크스페이스 경로/모드 · 역할 배정 정책 데스크톱 Project 대응
runs 오케스트레이션 런 — status(queued→running→done/failed/stale) · 목표 · claim 정보 작업 큐를 겸함 (DB-as-queue)
tasks 분해된 작업 그래프 노드 — 상태 · 담당 LLM 작업 보드 소스
rooms · messages 채팅방 · 메시지 (완결된 메시지만 — 스트리밍 델타는 저장 안 함) 대용량 본문은 Storage 오프로드
approvals 승인 요청 — 명령/경로/위험도 · 상태머신(§7) Realtime 구독 대상
events append-only 감사/타임라인 이벤트 INSERT 전용 정책으로 불변 강제
llm_sessions 등록된 LLM 세션 · capabilities 데스크톱 sessions 대응
runners 러너 등록 · 하트비트 · 버전 온라인 표시 · stale 판정
  • RLS 이중 정책 — 사용자 롤: 자기 owner_id 행만 · 러너 롤: 자기 소유자의 행만 + events 는 INSERT 전용. Supabase service_role 키는 러너에 두지 않는다(유출 시 전권 탈취). 주의(Codex P2): owner_id 필터만으론 부족하다 — 브라우저는 Supabase 에 직결되므로, 로그인된 브라우저(devtools·XSS)가 자기 소유 runs/tasks/messages/approvals 를 임의 UPDATE 해 완료·승인을 위조하고 감사 추적을 오염시킬 수 있다. 러너 전용 상태 전이(실행 상태·완료·결과 기록)는 롤별 컬럼/전이 정책 또는 SECURITY DEFINER RPC 로만 허용하고, 브라우저 롤에는 생성(INSERT)·승인 응답 등 사용자 몫의 전이만 연다.
  • 큐의 원자성 — 러너의 claim 은 조건부 UPDATE 로. Postgres 가 큐 역할을 하므로 별도 메시지 브로커가 필요 없다.
  • 무료 티어 한도 내 운용 — DB 500MB 급이므로 토큰 스트림을 행으로 저장하지 않는 것(§6)과 오래된 events 의 Storage 아카이브가 중요.
06

실시간 스트리밍

Supabase Realtime 의 세 모드를 용도별로 나눠 쓴다. 원칙: 휘발성 스트림은 DB 를 거치지 않는다.

모드 용도 왜
Broadcast LLM 토큰 델타 (start | delta | end | error) DB 를 거치지 않는 pub/sub — 초당 수십 건의 델타를 행으로 쓰면 무료 티어 DB 가 즉사한다. 유실돼도 완결 메시지가 DB 에 남으므로 무해. 단 반드시 private 채널(private: true + realtime.messages RLS 정책으로 룸 소유자만 join) — 공개 Broadcast 토픽은 테이블 RLS 밖이라, 토픽명이 유출/추측되면 타 클라이언트가 델타를 읽거나 위조할 수 있다 (Codex P2)
Postgres Changes runs · tasks · approvals 상태 변화 영속 상태의 변화 알림 — 놓쳐도 테이블 재조회로 복구 가능 (진실 원천 = DB)
Presence 러너 온라인/오프라인 · 실행 중 표시 연결 기반 생존 신호 — 하트비트 테이블의 즉시성 보완

07

승인 게이트 — 모바일 승인

이 아키텍처의 킬러 시나리오: PC 에서 런이 돌다가 위험 명령을 만나면, 외출 중인 내 폰으로 승인 요청이 오고, 승인하면 PC 가 이어서 실행한다. 데스크톱 ApprovalGate 의 destructive-pattern 분류(기본 차단 목록)를 그대로 심각도 시드로 쓴다.

승인 상태 머신 (approvals 테이블)

requested → pending → approved / denied / expired (TTL → 기본 거부)

safe 클래스는 정책 프리셋이 requested→approved 즉시 단락 · destructive 는 항상 차단 · 모든 전이는 events 에 기록

  • 알림 — 1차: 브라우저 Realtime 구독(열려 있을 때) · 2차: Web Push(PWA 로 설치 시 폰 잠금화면 알림). 이메일은 폴백.
  • 대기 중 러너 — 해당 작업 노드만 블록하고 승인 불필요한 다른 그래프 노드를 먼저 진행(speculative continue). 전체 대기 시 CLI 프로세스는 유휴 정지.
  • 타임아웃 = 기본 거부 — fail-closed. 데스크톱과 동일 원칙.
08

시크릿 전략

원칙: 실행이 로컬이면 키도 로컬이 기본. 클라우드에 올리는 시크릿을 최소화한다.

  • LLM API 키 / 구독 CLI 로그인 — 러너 머신에만 둔다(암호화 파일 또는 OS 키체인, CLI 로그인 상태는 Docker 볼륨). Supabase 에는 올라가지 않는다 → Supabase 계정이 뚫려도 LLM 키는 안전.
  • 러너 자격증명 — 러너 전용 Supabase 계정의 리프레시 토큰. service_role 키 사용 금지. 주의(Codex P1): 별도 러너 계정의 auth.uid() 는 소유자가 아니므로, "자기 owner_id 행만" RLS 아래에서는 runs 를 볼 수도 claim 할 수도 없다 — runner→owner 매핑 테이블(소유자가 승인한 러너 등록) 또는 러너 JWT 의 owner claim + 그것을 참조하는 전용 RLS 정책이 스키마에 선행되어야 한다.
  • Supabase Vault (선택) — 여러 기기에서 러너를 돌리고 키를 동기화하고 싶을 때만. 이때도 봉투 암호화로 저장.
  • Vercel 쪽 — 프론트는 anon 키만 가진다(공개 전제 + RLS 가 방어선). 서버리스 함수에만 필요 시 상위 권한.
09

보안 · 위협 모델

v1 의 "적대적 테넌트" 가정이 빠지고 "에이전트 출력은 여전히 적대적일 수 있다" 만 남는다. 단, 새 면(surface)이 하나 생긴다 — 계정 탈취 시 원격으로 내 PC 에 작업을 주입할 수 있다는 점.

위협 1차 통제 2차 통제
에이전트 생성 코드의 폭주 (rm -rf · 호스트 침범) Docker 컨테이너 경계 + 워크스페이스만 마운트 ApprovalGate destructive 차단 · path-guard 존속 · git 롤백
계정 탈취 → 원격 작업 주입 (v2 신규) Auth MFA 필수 · 세션 만료 짧게 위험 명령은 어차피 승인 필요 · 신규 기기 로그인 알림 · runners 승인제(러너 등록 토큰)
Supabase 데이터 유출 LLM 키·CLI 로그인은 애초에 클라우드에 없음(§8) RLS · 민감 본문 Storage 암호화
prompt-injection → 데이터 유출 (로컬 실행이라 이그레스 통제는 현실적으로 포기) 승인 게이트가 파일 밖 반출 명령을 잡음 · 잔여 리스크로 인정
악성 러너 위장 등록 러너 등록 = 1회용 페어링 토큰 + 소유자 승인 runners 테이블에 기기 지문 기록
정직한 한계. 컨테이너는 microVM 이 아니다 — 커널 취약점 앞에서는 뚫린다. 단일 사용자 · 본인 머신 · 본인 코드라는 전제에서 감수 가능한 수준이며, 이 전제가 깨지는 순간(타인에게 서비스) v1 의 microVM 티어로 승격해야 한다(§11).
10

라이선스 (ToS) — 구독 CLI 의 여지

v1 의 하드 제약 — 구독 OAuth 의 제3자/클라우드 사용 금지(Anthropic 2026-04 · Google 2026-03) — 는 "제3자 서버에서 실행" 이 문제였다. v2 는 실행이 사용자 본인 머신이므로 데스크톱 Fleet 과 같은 위치로 내려온다:

경로 v2 판정 근거 · 조건
구독 CLI 를 러너 컨테이너에서 (본인 로그인) 회색 — 개인용 한정 가능성 실행 주체·머신·구독이 모두 본인. 단 "원격 트리거 자동화" 라는 점은 명시 허용이 아님 — 개인 사용에 한정하고, 상용 전환 시 이 경로는 제외
BYO API 키 (CLI 를 API-키 env 로) 안전 v1 과 동일 — 전 CLI 지원. 기본 권장 경로
구독 OAuth 를 클라우드 러너로 (미래 v1 승격 시) 금지 v1 §3 그대로 — 승격 시 API-키 경로만 이관

운영 원칙: 기본값은 API-키, 구독 CLI 는 "본인 머신 러너에서만 사용 가능" 으로 UI 에서 명시하고, 제3자에게 서비스를 여는 순간 자동으로 비활성화되는 구조로 설계한다.

11

확장 경로 — v1 풀 클라우드로

v2 는 v1 의 축소판이 아니라 Phase 0.5 다. 상용 SaaS 수요가 확인되면 아래 순서로 승격하며, 데이터 모델·코어 엔진·승인 설계는 그대로 간다. 상세 설계는 v1 문서 (fleet-saas-infra-plan.html) 참조.

로드맵

Phase 기간 (1인 기준) 범위 완료 정의
0 · 러너 골격 2–4주 코어 엔진 서버 패키지 추출 · Supabase 프로젝트/스키마+RLS · 러너 데몬(runs claim→실행→기록) · CLI 이미지 1종(claude) CLI 로 삽입한 runs 행이 PC Docker 에서 완주하고 결과가 DB 에 남는다

2 · 승인 + 안정화 3–4주 approvals 큐 + Web Push · stale 런 복구(하트비트·resume) · events 아카이브 · 정책 프리셋 외출 중 폰 알림으로 승인하면 PC 가 이어서 실행한다

리스크 · 미해결 질문

리스크 영향 완화
PC 가 꺼져 있으면 실행 불가 구조적 — 이 설계의 본질적 트레이드오프 queued 대기 + 러너 오프라인 표시 · WoL/상시 미니PC · 급하면 v1 승격
Supabase Realtime 한도/유실 중 — 스트림 끊김·지연 Broadcast 는 휘발 전제(진실 원천 = DB) · 재조회 복구 · 한도 초과 시 Pro
구독 CLI 원격 트리거의 ToS 회색지대 중 — 계정 제재 가능성 기본값 API-키 · 구독 경로는 개인용 opt-in + 명시 경고 · 정책 변화 모니터링
계정 탈취 → 원격 작업 주입 (v2 신규 면) 중 MFA 필수 · 러너 페어링 승인제 · 위험 명령 승인 게이트 (§9)
Docker Desktop/WSL2 의존 낮음 — 러너 셋업 마찰 compose 원커맨드 셋업 문서화 · 향후 네이티브 러너 옵션
Supabase 벤더 종속 낮음 — 표면이 Postgres+WS 라 얇음 전부 표준 Postgres/Realtime 패턴 → self-host Supabase 또는 일반 Postgres+웹소켓으로 이전 가능

미해결 질문:

  • CLI 컨테이너 이미지 전략 — 3사 CLI 를 한 이미지에 vs 개별 이미지 (버전 갱신 주기가 달라 개별이 유리해 보임).
  • 구독 CLI 로그인 볼륨의 컨테이너 공유 시 세션 충돌 여부 — Phase 0 에서 실측.
  • 워크스페이스 로컬 디스크 vs git 체크아웃 기본값 — 개인용은 로컬 디스크가 자연스러우나 다중 러너 시 git 필요.
  • Web Push(PWA) 의 iOS 제약 수준 — 승인 알림 UX 의 관건.
