데스크톱 Fleet 을 "어디서든 브라우저로 쓰는" 형태로 만드는 최단 경로 계획서. 클라우드 백엔드(Supabase·Vercel)도 사지 않는다 — 내 PC 의 Docker 컨테이너 하나에 Fleet 서버·CLI·웹터미널을 담고, Cloudflare Tunnel / Tailscale 로 노출한다. 유일한 공사는 Electron IPC 를 WebSocket 으로 갈아끼우는 전송층 교체이며, 이 작업은 v1(풀 클라우드)·v2(Supabase 하이브리드)로 갈 때도 그대로 쓰이는 공통 기반이다.

01

요약

목표는 하나다 — "내가 어디서든(폰·노트북·외부 PC) 브라우저로 Fleet 을 쓴다." v1(풀 클라우드 SaaS)과 v2(Supabase 하이브리드)를 검토한 끝에, 이 목표만 놓고 보면 클라우드 구성요소가 하나도 필요 없다는 결론에 도달했다. 근거는 Fleet 의 구조 자체에 있다:

  • 코어 엔진은 Electron 비의존 순수 TS — 오케스트레이션 두뇌(src/main/core/*)는 어떤 Node 프로세스에서든 돈다.
  • renderer 는 타입드 브리지(window.fleet) 뒤에 있다 — 브리지 구현체만 IPC→WebSocket 으로 바꾸면 React UI 는 무변경.
  • 터널이 나머지를 해결한다 — 포트 개방·고정 IP·인증서·로그인 서버 전부 Cloudflare Tunnel(+Access) 또는 Tailscale 이 대신한다.

결과물은 컨테이너 하나에 담긴 두 개의 문이다:

문 경험 CLI 모드 구독제(ToS) 위상
① 웹터미널 브라우저 터미널에서 cd 프로젝트 && claude — 데스크톱과 똑같은 라이브 대화 TUI (인터랙티브) 정석 사용 — 사람이 앉아서 쓰는 그 자체
② Fleet 오케스트레이션 목표 입력 → 작업 그래프 → 멀티 LLM 협업 → 승인 → verify, 전부 브라우저 UI 헤드리스 (stream-json) — §5 회색 → API 키 폴백 상비
이 계획의 한 줄 요약. 새로 만드는 것은 오케스트레이션이 아니라 배선이다 — 엔진·CLI 스폰·verify 루프·승인 게이트는 지금 코드 그대로, Electron 이라는 껍데기만 웹서버로 바꾼다. 그리고 그 배선(IPC→WS)은 v2·v1 로 갈 때도 반드시 필요한 공통 선행 작업이라 버려질 수 없다.

세 계획서는 대체 관계가 아니라 같은 코어 위의 단계다. v3 가 실질적 Phase 0 이고, "PC 꺼져 있을 때도" 가 아쉬워지면 v2, 남에게 팔게 되면 v1 로 승격한다(§13).

04

문 ① 웹터미널 — TUI 직접 대화

"터미널에서 claude 로 접속해 대화하는 경험" 을 브라우저로 옮기는 문. 파싱하는 코드가 없으므로(읽는 주체 = 사람) CLI 버전 업데이트로 TUI 모양이 바뀌어도 아무 영향이 없고, 구독제의 의도된 사용 그 자체라 ToS 걱정이 없다.

  • ttyd — 컨테이너 셸의 PTY 를 WebSocket 웹터미널로 노출하는 검증된 단일 바이너리. 직접 구현할 것이 없다.
  • tmux (핵심) — 브라우저 탭을 닫거나 폰 화면이 꺼져도 세션이 컨테이너에 살아있다. 재접속 후 tmux attach 하면 Claude 가 작업하던 화면 그대로 복귀. 노트북에서 시작한 대화를 폰에서 이어받는 것도 이것으로 해결.
  • 구독 로그인 — 컨테이너에서 claude login 1회 → 상태가 로그인 볼륨(~/.claude 등)에 영속. codex·gemini 동일.
  • 모바일 — xterm.js 는 폰에서도 동작하나 TUI 특성상 화면이 좁다. tmux 상태줄 + 폰트 축소로 실용 수준은 확보되고, 본격 사용은 노트북 권장.
이 문만 먼저 열 수 있다. 문 ① 은 Fleet 코드 변경이 전혀 필요 없다 — 이미지에 CLI + ttyd + tmux 를 넣고 터널만 걸면 끝. 그래서 로드맵(§10)의 Phase A 로 분리해 하루 만에 먼저 가동한다.
05

문 ② 오케스트레이션 — 헤드리스는 유지된다

중요한 사실 관계를 먼저 못박는다: v3 에서도 오케스트레이션은 헤드리스 모드 (--output-format stream-json)를 쓴다. CLI 를 운전하는 주체가 사람이 아니라 기계(오케스트레이터)이기 때문이다 — 기계는 응답이 끝났는지, 어디가 본문이고 어디가 도구 호출인지, verify 를 돌릴 타이밍인지를 알아야 하고, 그건 화면(TUI)이 아니라 기계용 출력 계약에서만 안정적으로 읽을 수 있다. TUI 를 긁는 대안은 버전 업데이트마다 깨지는 스크린 스크레이핑이라 채택하지 않는다.

실행 흐름 — 폰에서 목표를 입력했을 때 (오케스트레이션 로직은 데스크톱과 동일, 굵은 단계만 신규 배선):

런 1회의 흐름

1 · 입력

WS fleet:project:run → 서버가 engine.runProject()
→

2 · 분해·배정

플래너가 작업 그래프 생성 · 역할↔LLM 배정 (동일)
→

3 · 실행

CLI 를 stream-json 으로 스폰 — 컨테이너 안 child process (동일)
→

4 · 스트림

파서 이벤트를 WS broadcast → 브라우저 라이브
→

5 · 승인

위험 명령 → fleet:approval:request → 폰 승인 카드 → 게이트 통과
→

6 · verify

test/lint GREEN 까지 루프 → 작업 보드 갱신 (동일)

즉 2·3·6(오케스트레이션의 본질)은 코드 무변경이고, 공사는 1·4·5 의 전송 통로에만 있다 — 그것이 §6 이다.

06

전송층 교체 — IPC → WebSocket

v3 의 유일한 실질 공사. Electron 배선판을 웹 배선판으로 1:1 번역한다:

지금 (Electron) v3 (웹서버) 비고
main 엔트리 src/main/index.ts 서버 엔트리 server/index.ts (신규) FleetEngine 조립 코드는 기존 것을 거의 그대로 — Electron 어댑터 2개만 교체
ipcMain.handle (요청-응답) WS 요청-응답 (id 매칭) 또는 REST POST 채널명(fleet:<domain>:<action>)·페이로드 타입 그대로 — src/shared/types.ts 가 계약
webContents.send (이벤트 push) WS broadcast (접속 클라이언트 전원) 스트리밍 start|delta|end|error 체계 그대로
preload 브리지 src/preload/index.ts WS 클라이언트가 같은 window.fleet 인터페이스 구현 React 컴포넌트 무변경 — 브리지 뒤가 IPC 인지 WS 인지 UI 는 모른다
renderer 로딩 (BrowserWindow) Vite 빌드 결과물 정적 서빙 같은 빌드, 서빙 방식만 변경
SecretCrypto = safeStorage src/main/secret-crypto.ts 파일 기반 암호화(키 파일 볼륨) 또는 env 주입 어댑터 교체 1
워크스페이스 폴더 다이얼로그 서버측 경로 목록/직접 입력 UI 어댑터 교체 2 — 컨테이너에 마운트된 경로 중 선택
ApprovalGate → renderer 모달 approval-bridge.ts 같은 게이트 → WS 이벤트 → 승인 카드 UI 게이트 로직·destructive 차단 무변경 · 응답 대기 시맨틱 동일 · 연결된 클라이언트가 없으면 타임아웃 = 거부(fail-closed)
  • 재접속 복구 — WS 단절 후 재접속 시 스냅숏(현재 rooms/tasks/승인 대기)을 먼저 내려주고 이후 이벤트를 잇는다. 이벤트 로그가 이미 있으므로 스냅숏 API 는 store 조회로 충분.
  • 동시 접속 — 단일 사용자·다중 기기(노트북+폰)는 허용: broadcast 라 자연 지원. 단 같은 store 를 쓰는 Electron 앱과 컨테이너 서버의 동시 기동은 금지(JSON store 동시 쓰기 충돌) — 컨테이너 store 볼륨을 데스크톱과 분리해 해결.
  • 알림 — 1차: 열려 있는 UI 의 승인 카드. 2차(선택): 서버가 Web Push 발송(PWA 설치 시 폰 잠금화면). iOS 제약은 §12.
07

컨테이너 구성

# 이미지
node:24-slim
 + claude / codex / gemini CLI   ← 버전 태그 고정 (자동 업데이트 금지)
 + git · 프로젝트 verify 툴체인
 + fleet-server (코어 엔진 + renderer dist)
 + ttyd · tmux

# compose 서비스
fleet    : fleet-server (WS + 정적 서빙)
ttyd     : 웹터미널 (같은 볼륨)
cloudflared : 터널 사이드카 (fleet·ttyd 를 각 호스트네임으로)

# 볼륨
workspace/   프로젝트 폴더 (호스트 바인드)
cli-auth/    CLI 로그인 상태 (~/.claude 등)
fleet-data/  store · 이벤트 로그 · 시크릿 키 파일
  • CLI 버전 고정 — 데스크톱과 달리 자동 업데이트에 노출되지 않는다. 새 CLI 버전은 이미지 재빌드 → stream-json 파싱 스모크 테스트 GREEN 확인 → 교체. 헤드리스 출력 계약이 깨지는 업데이트를 게이트에서 잡는다.
  • WSL2 — 워크스페이스는 WSL2 파일시스템 쪽에 두는 것이 I/O 성능상 유리 (Windows 경로 바인드는 느리다).
  • 재기동 안전 — 실행 중 런이 있으면 graceful drain(현재 task 완료까지 대기) 후 재기동. CLI 세션 resume 이 있으므로 중단돼도 이어받기 가능.
08

접근 · 보안

노출하는 것이 웹터미널(=원격 셸)과 오케스트레이터(=코드 실행 지시권)라는 점을 직시해야 한다. 계정이 뚫리면 내 PC 의 셸을 내주는 것과 같다. 따라서 터널 앞단 인증이 타협 불가 전제다.

위협 1차 통제 2차 통제
외부인 접근 (URL 노출·크리덴셜 탈취) Cloudflare Access(이메일 OTP/SSO + MFA) 또는 tailnet 한정 — 익명 도달 자체가 불가 접속 로그 · 새 기기 알림 · 세션 만료 짧게
계정 탈취 → 웹터미널 = 원격 셸 MFA 필수 · 터미널 호스트네임은 별도 Access 정책(더 엄격) 컨테이너 경계 — 호스트 전체가 아니라 마운트된 워크스페이스만 노출
에이전트 생성 코드 폭주 (rm -rf 등) ApprovalGate destructive 차단 (기존 그대로) 컨테이너 경계 · git 롤백 · path-guard 존속
승인 응답자 부재 중 위험 명령 타임아웃 = 기본 거부 (fail-closed) 승인 불필요 노드 우선 진행(speculative continue)
CLI 로그인 볼륨 유출 볼륨은 호스트 로컬 — 클라우드에 아무것도 안 올라감 디스크 암호화(BitLocker) 전제
웹터미널과 승인 게이트의 관계. 문 ② 는 위험 명령이 게이트에 걸리지만, 문 ① 은 사용자가 곧 셸이라 게이트가 없다. 이는 결함이 아니라 데스크톱과 동일한 신뢰 모델(본인=전권)이다 — 단 그만큼 문 ① 의 앞단 인증이 문 ② 보다 강해야 한다는 비대칭을 Access 정책에 반영한다.
09

구독제 · 헤드리스 포지셔닝

이 대화에서 확정한 사실 관계의 요약. 구독 OAuth 의 제3자/클라우드 사용은 금지(Anthropic 2026-04 · Google 2026-03)지만, v3 는 실행이 본인 머신이므로 데스크톱과 같은 위치다. 남는 리스크는 "구독 계정의 헤드리스 자동화" 에 대한 조임 — 하드 차단보다는 레이트리밋으로 서서히 올 가능성이 높고, 실제로 무거운 오케스트레이션이 Claude Max 한도를 소진시킨 실측 사례가 있다.

경로 모드 판정 조임이 와도
문 ① 웹터미널 + 구독 로그인 TUI · 사람 운전 안전 — 정석 사용 영향 없음 (사람 사용량이 곧 정상 사용량)
문 ② 오케스트레이션 + 구독 로그인 헤드리스 · 기계 운전 회색 — 개인용 한정, 한도 내 구독 한도 소진/정책 변경 시 ↓ 로 전환
문 ② 오케스트레이션 + API 키 헤드리스 · 기계 운전 안전 — 기본 폴백 ANTHROPIC_API_KEY env 하나로 전환, 코드 무변경 (LlmSession 추상화)

운영 원칙: 구독제 헤드리스는 "쓸 수 있는 동안 쓰는 할인" 으로 취급한다. 아키텍처와 비용 계산은 API 키 기준으로 세우고, 구독 경로가 죽어도 시스템은 죽지 않는다. 최후 폴백으로 CLI 를 아예 우회하는 ApiProvider(SDK 직접 호출 + 도구 루프) 경로도 코어에 이미 존재한다.

로드맵

Phase 기간 (1인) 범위 완료 정의
A · 웹터미널 먼저 1–2일 CLI+ttyd+tmux 이미지 · compose · Cloudflare Tunnel+Access (Fleet 코드 변경 0) 폰 브라우저에서 claude 로 접속해 대화하고, 끊었다 붙여도 tmux 세션이 살아있다
B · 전송층 교체 2–3주 server/index.ts 배선판 · IPC→WS 핸들러 이사 · window.fleet WS 브리지 · 어댑터 2개(시크릿·경로) · renderer 정적 서빙 코어 vitest 전량 GREEN 유지 + 브라우저에서 목표 입력→오케스트레이션 런 완주
C · 승인 + 안정화 1–2주 승인 카드 UI · 재접속 스냅숏 복구 · graceful drain · (선택) Web Push 외출 중 폰으로 승인하면 PC 가 이어서 실행한다
D · 확장 판단 수요 발생 시 "PC 꺼짐" 이 아프면 → v2 (Supabase 계층 추가) · 상용화 → v1 (§13) —

Phase A 를 분리한 이유: 가장 원하는 경험(터미널 라이브 대화)을 코드 변경 없이 즉시 확보하고, 터널·인증·컨테이너 운영을 실전에서 먼저 검증한 뒤에 Phase B 공사를 시작하기 위함이다. 데스크톱 Electron 앱은 전 기간 병행 사용 가능하다(store 볼륨 분리 전제, §6).
