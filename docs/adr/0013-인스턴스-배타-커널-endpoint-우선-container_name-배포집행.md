## 맥락

Workbench 코어는 「같은 코디네이션 영역(`<common gitdir>/fleet/`)을 보는 살아있는 엔진 인스턴스는
하나」를 전제로 선다. 이 전제가 깨지면 두 곳이 동시에 무너진다.

- **자문 락(§W-3)** — 락 배타 범위는 Linux **network namespace** 인데 레포 공유 범위는 **파일시스템**이다.
  같은 레포 볼륨을 문 두 인스턴스가 서로 다른 net ns 에 있으면 서로의 endpoint 를 보지 못해 **양쪽 다
  획득에 성공**한다(이중 소유 = fail-open).
- **잔재 회수(§W-16 ②)** — 「기록된 인스턴스 마커 ≠ 현 인스턴스 ⇒ 이전 PID ns 소멸 = 트리 사망 확정」은
  «같은 영역을 보는 인스턴스가 동시에 둘 이상 없다» 를 전제로만 성립한다.

스펙은 이 전제를 `open(<area>/active-instance.json,'wx')` 로 집행한다고 썼지만, 착수 전 감사에서 두 구멍이
실측으로 드러났다.

1. **순서 미판정** — `wx` 와 커널 endpoint bind 의 선후가 어느 문서에도 없다. `wx` 를 먼저 하면 승자가
   bind 하기 전 창에서 다른 부팅의 생존 probe 가 성공해 **같은 컨테이너 안에서** 이중 인스턴스가 성립한다.
2. **배포 계약이 문면뿐** — `container_name` 은 레포 어디에도 없었고 `--scale fleet=3` 이 **경고 없이**
   성공했다. 즉 §W-16 ②의 안전 논증이 기대는 「단일 컨테이너」가 아무것도 강제하지 않는 산문이었다.

## 결정

**① 획득 순서를 「커널 endpoint bind → 성공 시에만 파일 점유」로 고정한다.** bind 가 커널 배타이므로
파일을 만지기 전에 「이 net ns 에 살아있는 인스턴스가 있는가」가 이미 확정된다. 그 결과 스펙의 4분기가
다음으로 재사상된다 — bind 가 `EADDRINUSE` 면 **파일을 읽지도 않고** 대기, bind 성공이면 잔재를 회수하되
마커 일치 여부는 회수의 **증거 등급**(커널 증명 / 배포 전제 의존)만 결정한다.

**② 파일 프리미티브는 `wx` 가 아니라 tmp + `link`(create-only)로 한다.** 발행과 회수 **양쪽 모두**.
`link` 의 `EEXIST` 가 경합 패배의 권위 신호이며, 패자는 덮어쓰지 않고 물러난다.

**③ 「인스턴스는 하나」 전제를 `deploy/docker-compose.yml` 의 `container_name: fleet-server` 로 집행한다.**
compose 는 이 키가 있는 서비스의 `scale>1` 을 거부한다. 검증은 3층 — smoke 의 키 단언(base·override 양쪽) ·
smoke 의 **행동** 검사(`up --dry-run --scale fleet=2` 거부 + 양성/음성 통제) · PR 게이트에서 도는
`scripts/deploy-workbench-pin.test.ts` 의 서비스 블록 스코프 핀.

## 고려한 대안 / 기각 사유

- **파일(`wx`) 단독 배타** → 기각. `wx` 는 **파일이 없을 때의 생성**만 배타한다. 잔재가 있는 상태(=회수
  분기)에서는 아무도 배제하지 않아 두 회수자가 **둘 다 성공**한다(실측). 또 `wx` 는 바이트 이전에 이름을
  노출해, 발행 도중 크래시가 「존재하는 빈 파일」을 남기고 그것이 「판정 불가 = 자동 삭제 금지」 규칙에
  걸려 **크래시 1회 = 운영자 개입 없이 복구 불가**가 된다.
- **파일 먼저 → endpoint 나중** → 기각. 위 맥락 ①의 창이 열린다.
- **락 키(`r`)를 생존 probe 로 재사용** → 기각. 락 키 3종은 변이 구간에만 잡히는 **일시 보유**라, 락을
  쥐지 않은 idle 인스턴스가 「사망」으로 판정돼 회수된다(fail-open). 반대로 `r` 을 인스턴스 수명 내내
  보유하면 모든 레포 변이가 영구 정지한다. → 전용 키(`i`)를 신설했다.
- **`deploy.replicas` 제약·기동 시 자체 거부만으로 충분** → 기각. 전자는 swarm 전용이라 compose up 경로에
  효력이 없고, 후자는 **런타임 층 하나에 안전을 몰아** 그 층의 전제를 스스로 증명하게 만든다(순환).
- **행동 검사를 nightly 로 위임** → 기각. 위임처가 레포에 **없다**(유일 cron 은 electron 전용). 그리고
  `up --dry-run` 은 실측상 네트워크·볼륨·컨테이너를 하나도 만들지 않고 초 단위로 끝나므로 미룰 이유가 없다.

## 결과 (Consequences)

- **얻는 것**: 이중 인스턴스가 3층으로 막힌다 — **같은 net ns** 는 커널 endpoint 가, **경합**은 파일
  create-only 가, **다른 컨테이너**는 배포 계약(③)이 담당한다. 회수 판정이 마커에 의존하지 않게 되어
  (마커는 증거 등급만) 마커 충돌이 판정을 뒤집지 못한다.
  ⚠ 세 층은 **서로 다른 구간**을 덮으며 대체 관계가 아니다 — 특히 ③이 깨진 구간을 ①②가 메우지 않는다.
- **감수하는 비용**: ⓐ`container_name` 고정으로 **호스트당 fleet 스택 1개**가 된다 — 같은 호스트의 두 번째
  compose 프로젝트는 이름 충돌로 loud-fail 한다(집행 자체가 목적이므로 수용).
  ⓑ**cross-namespace 배타를 런타임에서 내준다**: 결정 ①이 배타를 커널 endpoint(net ns 스코프)에 얹었으므로,
  같은 워크스페이스를 가리키는 **다른 이름의 스택**·이름 없는 `docker run`·호스트 직접 실행에서는 두 인스턴스가
  **둘 다 획득에 성공**하고 나중 쪽이 앞선 레코드를 `deployment-premise` 등급으로 회수한다. 런타임 층은 그
  구간을 **차단하지 않고 기록**한다 — 그 구간의 안전은 오직 ③이 진다(README 「단일 인스턴스 전제」에 명시).
  대안이었던 「파일(`wx`) 단독 배타」는 ns 무관이라 이 성질을 갖지 않았지만, 회수 경로에서 두 회수자를 모두
  성공시키는 결함이 있어 기각됐다 — 즉 이 비용은 그 트레이드오프의 대가다.
  ⓒ`--scale` 행동 검사는 `deploy/smoke.sh` 에 있어 **머지 후** deploy 워크플로에서 돈다(PR 게이트 방어는
  scripts 핀이 담당).
  ⓓ**모듈만 착지했고 부팅 배선은 후속 PR** 이다 — 그때까지 실제로 집행되는 것은 ③(배포층) 하나뿐이다.
- **재검토 트리거**: 데스크톱 Workbench(#255)가 오면 cross-surface 조정이 되살아나 ①의 전제가 바뀐다 ·
  컨테이너를 여러 대로 늘리는 요구(수평 확장)가 생기면 이 ADR 전체가 재검토 대상이다 · compose 가
  `container_name` + scale 조합의 거부를 완화하면 smoke 행동 검사가 먼저 RED 로 알린다.
