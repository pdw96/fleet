## 맥락

"Fleet 을 어디서든 브라우저로 쓴다" 요구에서 SaaS 전환 검토가 시작됐다. 1차 사용자는 소유자
본인(판매 아님)이고, 구독 CLI 의 OAuth 는 공식 도구 밖 사용이 금지(Anthropic 2026-04 ·
Google 2026-03)라 제3자 서버 실행 경로가 막혀 있으며, 코어 엔진은 Electron 비의존 순수
TS + 포트/어댑터 구조다. 세 아키텍처를 문서화해 비교했다(`docs/fleet-saas-infra-plan*.html`).

## 결정

**v3 터널 셀프호스트를 첫 단계로 채택한다** — 로컬 Docker **compose 스택**(Fleet 서버 = 코어
엔진 + renderer 정적 서빙 + CLI 를 담는 `fleet` 서비스와, 웹터미널 `ttyd` 서비스를 **분리**해
의도된 볼륨만 공유 — `fleet-data`(store·이벤트 로그·시크릿)는 서버 전용, 터미널 셸에는 미마운트)
를 Cloudflare Tunnel(Access)/Tailscale 로 노출하고, 유일한 실질 공사를 IPC→WebSocket 전송층
교체로 좁힌다. 단일 컨테이너에 웹터미널을 동거시키면 원격 셸이 store·시크릿까지 읽어 문서화된
피해 반경(workspace+cli-auth)이 거짓이 된다. 근거: 단일 사용자 목표에 클라우드
구성요소가 불필요하고, 실행이 본인 머신이라 구독 CLI ToS 위치가 데스크톱과 동일하며, 전송층
추상화는 이후 승격(v2·v1)에서도 재사용된다(단 인증·테넌트 계층은 승격 시 추가 — 프로토콜
그대로 이관 아님).

## 고려한 대안 / 기각 사유

- **v1 풀 클라우드 SaaS** (K8s + Kata microVM 멀티테넌트): 판매 전제의 격리·과금·이그레스
  인프라(GA ~$10–30k/월)가 현 목표에 과잉 → 상용화 시점의 승격 목표로 보존, 지금은 기각.
- **v2 Vercel + Supabase 하이브리드** (클라우드 관제탑 + 로컬 러너): "PC 꺼져 있어도 UI·예약
  생존" 이 장점이나 Store 이식·Realtime 배선·Auth 연동이 추가 공사 → 그 가용성이 실제로
  아파질 때의 승격 목표로 보존, 첫 단계로는 기각.
- **웹터미널만** (Fleet 코드 변경 0): 오케스트레이션 원격 사용이 빠짐 → 기각이 아니라 v3 의
  Phase A 로 흡수(가장 먼저 가동).

## 결과 (Consequences)

- 좋은 점: 운영비 ≈ $0 · 공사 최소(전송층 + 어댑터 2) · 구독 CLI 경로 보존 · 코어 vitest 로
  이식 검증 가능.
- 감수하는 비용: PC 꺼짐 = 전면 다운(구조적) · 웹터미널 = ApprovalGate 밖 원격 셸(피해 반경 =
  workspace + cli-auth, Access MFA 로 완화) · 브라우저 배포에서 Electron guards 소멸 →
  Origin/identity 서버 자체 검증 신설 필요.
- 재검토 트리거: "PC 꺼짐" 이 반복적으로 아프면 v2 승격 검토, 외부 사용자 수요가 생기면 v1
  승격 검토(#193 Phase D). 구독 헤드리스 정책 변화 시 API 키 기본 전환.
