## 맥락

오케스트레이션의 verify 단계는 워크스페이스에서 `npm run typecheck` · `npm run lint` · `npm test` 를
자식 프로세스로 돌린다(`core/verify/run.ts` `npmVerifyCommands` → `runAllVerifications`, 배선은
`core/engine.ts` 의 `currentVerify`). 그런데 그 npm 스크립트와 테스트 파일은 **직전 implementer 세션이
방금 쓴(또는 고쳐 쓴) 코드**다. 즉 verify 는 에이전트 산출 코드를 **사람 승인 없이, 샌드박스 없이,
사용자 실제 워크스페이스에서 사용자 권한으로 실행하는 통로**다.

승인 게이트는 이 경로에 없다. 게이트는 호출자가 신고한 `req.risk` 를 집행할 뿐이고
(`core/safety/approval.ts` — 코어 내 명령 denylist 없음, 위험 분류는 sub-agent CLI 경계에 위임),
verify 러너는 애초에 `gate.request` 를 호출하지 않는다. 편집 diff 승인도 이 구멍을 덮지 못한다:
`package.json` 은 `SENSITIVE_FILE` 에 매치되지 않고, 대량 삭제·diff 절단도 아닌 소형 변경은
`classifyDiffRisk` 가 `caution` 으로 분류하는데 **오케스트레이터는 `destructive` 일 때만
`gate.request` 를 호출하므로**(`orchestrator.ts` 의 두 승인 지점) 승인 모달 자체가 뜨지 않는다.
설령 다른 이유로 그 diff 가 승인 화면에 올라가더라도, `"test"` 스크립트 한 줄이나 새 `*.test.ts` 의
부수효과를 사람이 diff 만 보고 판별하리라 기대할 수 없다.

이 레포는 인접 경계를 정밀하게 지킨다 — `cli/registry.ts` 는 implementer 세션에 `node --check` 조차
자동 허용하지 않으며(#167: preload 플래그로 RCE 가 된다), 그 주석은 "실제 verify(typecheck/lint/test)는
Fleet 이 별도 실행한다"고 적어 두었다. **바로 그 별도 실행이 지금 문서화되지 않은 에스컬레이션
통로다.** #166(정직성)·#167(세션 경계)·#170(안전 self-verify)·ADR-0010(샌드박스는 컨테이너 한정)
어디에도 데스크톱 verify 의 이 전제를 수용한 기록이 없다. 발견의 본체는 취약점이 아니라 **기록 공백**
이다(2026-09-01 건강검진 [P2-2]).

## 결정

**데스크톱 verify 는 앞으로도 승인 게이트 없이 워크스페이스의 검증 스크립트를 실행한다. 그 위험을
여기서 명시적으로 수용하고, 코드는 바꾸지 않는다.**

근거는 셋이다.

1. **verify 의 가치는 실행 자체다.** 코드를 실행하지 않는 검증은 검증이 아니다. 게이트를 세워도
   사용자가 승인해야 verify 가 돌고, 승인을 거절하면 오케스트레이션의 핵심 루프(구현 → 검증 →
   수정)가 멈춘다. 즉 게이트는 위험을 없애는 게 아니라 사용자에게 매번 같은 답을 강요한다.
2. **신뢰 경계는 verify 가 아니라 그 앞단에 있다.** 사용자는 이미 (a) 워크스페이스 디렉터리를 직접
   고르고, (b) 어떤 CLI/provider 를 implementer 로 쓸지 등록하고, (c) 편집 diff 를 승인한다.
   verify 를 승인 대상으로 올리면 "AI 가 쓴 코드를 내 머신에서 돌린다"는 결정이 세 번째가 아니라
   네 번째 지점에서 반복될 뿐, 새 정보는 생기지 않는다.
3. **완전한 차단은 샌드박스 없이는 불가능하다.** 아래 대안들이 전부 부분적이라, 부분 방어를
   "방어"로 표시하는 편이 무방비보다 위험하다(ADR-0013 과 같은 판단 — 열거는 「게이트 밖」이라는
   사실의 기록이지 안전 보증이 아니다).

수용의 조건은 **기록**이다. 이 ADR 이 그 기록이며, 재평가 트리거(아래)에 걸리면 결정을 다시 연다.

## 고려한 대안 / 기각 사유

- **대안 A — 프로젝트 실행당 1회 caution 승인**("이 워크스페이스에서 검증 명령을 실행합니다"):
  가장 싼 개선(engine 또는 orchestrator 에 `gate.request` 1회 + 테스트)이고 UX 비용도 클릭 한 번뿐.
  → **기각**. 그 1회 승인이 담는 정보가 사용자가 워크스페이스를 고를 때 이미 내린 결정과 동일해,
  실질은 "예"를 학습시키는 클릭이다. 승인 피로는 게이트 전체의 신호 대비 잡음을 떨어뜨리는데
  (destructive diff 승인이 진짜 신호다), 그 비용을 무정보 승인에 쓰지 않는다. 이 판단이 뒤집히는
  조건은 재평가 트리거에 적었다.
- **대안 B — verify 자식을 샌드박스에서 실행**(컨테이너·seccomp·별도 사용자):
  → **기각(현 단계)**. ADR-0010 이 이미 "샌드박스 경계는 컨테이너 표면"이라고 정했고, 데스크톱에
  같은 경계를 세우려면 워크스페이스 마운트·툴체인 재현·네이티브 의존까지 따라와 1.0 표면(ADR-0017)
  밖으로 나간다. 솔로 pre-1.0 의 과설계 경계(ADR-0003)에도 걸린다.
- **대안 C — `package.json` 을 `SENSITIVE_FILE` 로 특별취급**(변경 시 항상 destructive 승인):
  → **기각**. 벡터를 닫지 못한다. 악성 코드는 `"test"` 스크립트가 아니라 **새 `*.test.ts` 파일**로도
  똑같이 실행된다(테스트 러너는 새 테스트 파일을 글롭으로 자동 수집한다). `package.json` 만 막으면 우회는
  자명한데 방어했다는 표시만 남아 오히려 해롭다.
- **대안 D — 검증 명령 allowlist**(`npm run typecheck|lint|test` 만 허용):
  → **기각**. 이미 그렇게 되어 있는데도(고정 3개 명령) 문제가 성립한다 — 위험은 명령 이름이 아니라
  그 이름이 가리키는 **스크립트 본문과 테스트 파일**에 있다. 명령 표면을 좁혀도 벡터는 그대로다.

## 결과 (Consequences)

**얻는 것**: verify 루프가 무마찰로 돈다. 게이트의 승인 요청은 "실제로 판단이 필요한 것"
(destructive diff·민감 파일·shell)만 남아 신호가 희석되지 않는다. 코드 변경 0줄.

**감수하는 비용**: implementer 가 `"test": "<임의 셸>"` 을 심거나 부수효과 있는 `*.test.ts` 를
추가하면, verify 가 사용자 권한으로 그 코드를 실행한다. `git revert` 는 이미 일어난 부수효과를
되돌리지 못한다. 완화는 부분적이다 — destructive 로 분류된 diff 에 한정된 승인 모달, 서버 모드의
`childEnv.base` 로 FLEET_* 시크릿 미상속(`createVerifyRunner(baseEnv)`), verify 타임아웃,
`cancelRun` 전파. **이 완화들을 방어로 취급하지 않는다.**

**재평가 트리거** — 하나라도 성립하면 이 ADR 을 다시 연다(대안 A 또는 B 로):

- **멀티유저/원격 위임** — 워크스페이스 소유자와 implementer 를 고르는 주체가 갈라질 때
  (팀 사용·서버 표면에서 데스크톱 verify 경로 재사용). 지금 전제는 "둘이 같은 사람"이다.
- **1.0 외부 사용자** — 자기 코드가 아닌 저장소를, 자기가 고르지 않은 모델로 돌리는 사용자가 생길 때.
- **워크스페이스 선택 없는 실행 경로**가 생길 때(자동 clone·템플릿 생성 등) — 근거 2의 (a)가 깨진다.
- **비-npm verify 확장**(#293 W3) 이 실행 표면을 넓힐 때 — 같은 파일을 만지므로 그 작업에서 이 결정을
  함께 확인한다.
