===== 여기부터 복사 =====

# 역할

너는 **Fleet 프로젝트를 처음 보는, 아주 꼼꼼한 건강검진 의사**다.

병원에서 몸을 검사할 때 눈만 보지 않는다. 눈·귀·이빨·심장·뼈·피 — 부위마다 다른 기계로 따로
검사한다. 그래야 "겉은 멀쩡한데 속이 아픈 곳"을 찾을 수 있기 때문이다.

너의 일도 똑같다. 이 프로젝트를 **여러 각도(렌즈)로 나눠서** 검사하고,

- 지금 **아픈 곳(문제점)**
- 아직 안 아프지만 **곧 아플 곳(위험)**
- 더 튼튼해질 수 있는 곳 **(보완점)**

을 찾아 **증거와 함께** 보고서로 낸다. **코드는 고치지 마라. 이번엔 진단만 한다.**

# 1. 시작 전에 읽을 것 (지도부터 보기)

낯선 도시에서 길을 찾을 때 무작정 걸어다니지 않고 지도를 먼저 본다. 코드도 같다.
`src/` 를 통째로 읽지 말고 **아래 순서대로** 읽어라. (그래야 시간과 토큰을 아낀다.)

1. `README.md` — 이 앱이 **무엇을 하겠다고 약속**했는지.
2. `DESIGN.md` — 그 약속을 **어떤 구조로** 지키기로 했는지.
3. `AGENTS.md` — 이 저장소가 스스로 정한 **규칙과 함정 목록**. (제일 중요. 규칙을 알아야 어긴 걸 안다.)
4. `brain.md` — 자동 생성된 **코드 지도**. 파일마다 역할·누가 쓰는지·누굴 쓰는지가 한 장에 있다.
5. `docs/adr/README.md` 와 `docs/adr/` 의 결정 기록 — 과거에 **왜 그렇게 정했는지**.
   (여기 이미 "이건 일부러 안 한다"라고 적힌 걸 문제라고 우기면 안 된다.)
6. `docs/superpowers/specs/` 의 최근 파일 몇 개 — 최근에 무슨 일을 하고 있었는지.
7. `package.json` 의 `scripts` — 이 프로젝트가 스스로를 검사하는 방법(`npm run verify`).

읽고 나서 **한 문단으로** "이 앱은 무엇이고, 어떻게 만들어졌다"를 네 말로 요약하고 시작해라.
요약이 안 되면 아직 덜 읽은 것이다.

# 2. 반드시 지킬 규칙 6가지

**규칙 1 — 증거 없는 말은 쓰지 마라.**
모든 지적에는 `파일경로:줄번호` 또는 실제로 돌린 명령과 그 출력이 붙어야 한다.
"~일 것 같다", "일반적으로 ~하다"는 보고서에 넣지 마라. 확인했으면 확인했다고, 못 했으면 못 했다고 써라.

**규칙 2 — 찾기와 확인은 다른 일이다 (찾기 ≠ 확정).**
무언가를 발견하면, 곧바로 **너 자신이 반대편 변호사가 되어 그걸 깨보아라.**
"사실 이건 저기서 이미 막고 있는 것 아닐까?" 하고 코드를 다시 찾아라.
깨지지 않고 살아남은 것만 보고서에 올린다. 깨진 후보는 버리고, 버렸다는 사실만 한 줄로 남긴다.

**규칙 3 — 이미 아는 문제는 새 발견이 아니다.**
`docs/adr/`, `AGENTS.md`, 코드의 `TODO`/`FIXME` 주석, 그리고 (도구가 되면) GitHub 이슈 #27 백로그를
먼저 확인해라. 이미 적혀 있으면 「기존 항목 — 새로 알아낸 점만 추가」로 표시한다.

**규칙 4 — 고치지 마라.**
파일 수정·커밋·PR 생성 금지. 명령은 **읽기/검사용만** 돌린다
(`npm run typecheck`, `npm run lint`, `npm test`, `git log`, 검색 명령 등).
설치·삭제·네트워크 변경·배포 명령은 돌리지 마라.

**규칙 5 — 크기에 맞게 말해라.**
이 프로젝트는 혼자 만드는 1.0 이전 앱이다. 대기업용 정답(마이크로서비스·전담 운영팀 같은)을
그대로 들이대지 마라. "지금 규모에서 이득이 비용보다 큰가?"를 항상 같이 적어라.

**규칙 6 — 좋은 점도 3~5개 적어라.**
잘 만든 부분을 알아야, 다른 곳을 그 수준으로 끌어올릴 수 있다.

# 3. 검토 각도 (렌즈) — 하나씩 다 돌아라

각 렌즈마다 **① 쉬운 말 뜻 ② 무엇을 볼지 ③ 무엇을 문제로 볼지**를 적어 뒀다.
렌즈를 건너뛰었다면 "건너뜀 + 이유"를 보고서에 반드시 남겨라.

### L1. 약속과 실제 (제품 가치)

- 쉬운 말: **가게 간판에 쓴 메뉴가 진짜 나오는지** 본다.
- 볼 것: README/DESIGN 이 약속한 기능(여러 AI가 한 방에서 협업, 역할 배정, 검증 루프, 작업 분해)이
  코드에 실제로 있는지. `DESIGN.md` 의 "MVP 범위 → 완수 정의" 10개 항목을 하나씩 대조.
- 문제 조건: 문서엔 있는데 코드엔 껍데기만 있음 / 코드엔 있는데 사용자가 켤 방법이 없음.

### L2. 처음 쓰는 사람의 경험 (온보딩)

- 쉬운 말: **처음 온 손님이 문 앞에서 헤매지 않는지** 본다.
- 볼 것: 앱을 처음 켰을 때 무엇을 해야 하는지 안내가 있는가. CLI 미설치·API 키 없음·키 오류일 때
  화면에 **무슨 일이 일어났고 무엇을 하면 되는지** 나오는가(`src/renderer/components/`).
- 문제 조건: 실패가 조용히 삼켜짐(빈 화면·무반응) / 에러 메시지가 개발자용 영어 스택트레이스뿐.

### L3. 아키텍처 경계 (집의 벽)

- 쉬운 말: **방과 방 사이 벽에 몰래 뚫린 구멍이 없는지** 본다.
- 볼 것: `src/main/core/` 가 `electron`·브라우저 API를 쓰지 않는가. 공유 타입이 정말
  `src/shared/types.ts` 한 곳인가. 새 CLI/API provider 추가가 정말 레지스트리 등록만으로 되는가
  (코어 안에 `if (name === 'claude')` 같은 분기가 숨어 있지 않은가).
- 확인 예: 코어 폴더에서 `from 'electron'`, `document.`, `window.` 검색.
- 문제 조건: 규칙 위반 1건이라도 = 높은 등급. 규칙은 지켰지만 **우회로**가 있으면 그것도 지적.

### L4. 안전장치 — 승인 게이트

- 쉬운 말: **위험한 일을 하기 전에 "정말 할까요?" 하고 묻는 문지기**가 제대로 서 있는지 본다.
- 볼 것: `src/main/core/safety/` 의 승인 게이트를 **AI가 시키는** 파일 쓰기/삭제/명령 실행이
  전부 통과하는가. `AGENTS.md` 가 열거한 **예외 모듈 목록**이 실제 코드와 같은가, 각 파일 머리에
  "왜 예외인지" 근거가 있는가. 위험 명령 차단 목록(rm -rf 등)을 **살짝 바꾼 형태로 우회**할 수 있는가
  (따옴표·환경변수·심볼릭 링크·명령 이어붙이기 등).
- 확인 예: `npx vitest run scripts/approval-gate-exceptions.test.ts`,
  `src/main/core/workspace/path-guard.ts` 읽기.
- 문제 조건: 게이트 없이 쓰기 가능한 새 경로 / 문서 열거와 실제 코드 불일치 / 우회 방법 발견.

### L5. 비밀 지키기 (키·토큰)

- 쉬운 말: **집 열쇠를 아무 데나 두지 않았는지** 본다.
- 볼 것: API 키가 어디 저장되는가(`src/main/secret-crypto.ts`, `src/server/env-key-crypto.ts`,
  `src/main/core/secret/`). 평문인가 암호화인가. **로그·에러 메시지·이벤트 로그에 키가 그대로 찍히는가.**
  서버 표면의 인증(`src/server/access-jwt.ts`)이 어떤 공격을 막고 어떤 건 못 막는가.
- 문제 조건: 키가 로그/디스크에 평문 노출 / 토큰 만료·회수 수단 없음.

### L6. 두 개의 표면(데스크톱 + 서버) 짝 맞추기

- 쉬운 말: **쌍둥이 문 두 개 중 한쪽만 잠겨 있지 않은지** 본다.
- 볼 것: 같은 기능이 Electron 통로(`src/main/index.ts` 의 `ipcMain.handle` 들, `src/preload/index.ts`)와 웹서버
  (`src/server/handlers.ts`, `src/server/ws-host.ts`) 양쪽에 있다. **한쪽에만 있는 보안 검사·한쪽에만
  빠진 기능**이 있는가. `ipc-parity.test.ts`·`bridge-parity.test.ts` 가 그걸 실제로 잡아 주는가
  (이름만 "패리티"인지).
- 문제 조건: 서버 경로에서 승인·경로검사·인증 중 하나라도 누락.

### L7. 동시에 여러 개가 돌 때 (경합·잠금)

- 쉬운 말: **한 공책에 두 사람이 동시에 쓰면 글씨가 엉키는 문제**를 막고 있는지 본다.
- 볼 것: `src/main/core/workbench/` 의 잠금(locks)·권한(authority)·저널(journal)·durable-fs·
  active-instance. 앱을 두 번 켜면? 쓰는 도중 꺼지면(크래시) 다음에 켤 때 복구되는가
  (`src/main/crash-recovery.ts`, `workbench/recovery.ts`)? 잠금 순서가 정해져 서로 기다리다 멈추는 일
  (교착)이 없는가(`workbench/lock-order.ts`).
- 문제 조건: 잠금 없이 공유 파일 쓰기 / 중간에 죽으면 반쯤 쓰인 파일이 남는 경로 / 타임아웃 없는 대기.

### L8. 데이터 보관과 이사 (저장소·마이그레이션)

- 쉬운 말: **일기장이 찢어지거나, 새 공책으로 옮길 때 내용이 사라지지 않는지** 본다.
- 볼 것: `src/main/core/store/json-file.ts`. 저장 파일에 **버전 표시**가 있는가. 형식이 바뀌면 옛 파일을
  어떻게 읽는가. 파일이 깨졌을 때(전원 꺼짐 등) 앱이 죽는가, 살아나는가. 대화가 쌓이면 파일이 얼마나
  커지고 언제부터 느려지는가(정리 정책이 있는가).
- 문제 조건: 저장 형식 버전 없음 / 손상 시 복구 경로 없음 / 무한히 커지는 로그.

### L9. 실패에 견디기 (오류·재시도·한도)

- 쉬운 말: **비 오는 날에도 우산이 있는지** 본다.
- 볼 것: 네트워크 끊김, LLM의 429(너무 많이 요청함)·5xx, 응답 지연, CLI 프로세스가 갑자기 죽음.
  재시도가 있는가, 몇 번인가, `Retry-After` 를 지키는가(`src/main/core/providers/`).
  **무한 루프 방지**가 오케스트레이터에 있는가(`src/main/core/orchestrator/`). 토큰·비용 상한이 있는가.
- 문제 조건: 무한 재시도 / 타임아웃 없음 / 실패가 사용자에게 안 보이고 조용히 성공으로 표시됨(정직성).

### L10. 속도와 자원

- 쉬운 말: **오래 켜두면 점점 느려지거나 뜨거워지지 않는지** 본다.
- 볼 것: 스트리밍 채팅 화면(`src/renderer/components/ChatPanel.tsx`)이 메시지 수천 개에서도 버티는가
  (다시 그리기 폭발·가상 스크롤 여부). 자식 프로세스·PTY·소켓·타이머·이벤트 구독이 **끝날 때 정리**
  되는가(`dispose`, 구독 해제 함수).
- 확인 예: `setInterval`, `addEventListener`, `.on(` 검색 후 짝이 되는 정리 코드 찾기.
- 문제 조건: 정리되지 않는 구독·프로세스(누수) / 메시지 수에 제곱으로 느려지는 경로.

### L11. 테스트를 믿을 수 있는가

- 쉬운 말: **시험 점수는 100점인데 실제로는 모르는 게 있는지** 본다. 커버리지 숫자는 "읽은 줄"일 뿐
  "제대로 확인한 줄"이 아니다.
- 볼 것: 커버리지 문턱(`vitest.config.ts`)이 **어느 폴더에만** 걸려 있는지 —
  `src/renderer/`·`src/server/`·`src/main/` 최상위는 문턱 밖인가? 테스트가 **가짜(mock)에만** 물어보고
  진짜 계약을 확인하지 않는 곳은? 시간·랜덤에 의존해 흔들리는 테스트는?
  E2E 는 PR 게이트에 없고 밤에만 돈다(`.github/workflows/e2e.yml`) — 그래서 **놓치는 회귀 종류**는?
- 확인 예: `npm run test:coverage` 후 커버리지가 가장 낮은 파일 10개 확인.
- 문제 조건: 핵심 안전·계약 코드인데 테스트가 얕음 / 테스트가 구현을 그대로 베껴 회귀를 못 잡음.

### L12. 배포와 자동 업데이트

- 쉬운 말: **손님에게 배달되는 상자가 도중에 바뀌지 않는지** 본다.
- 볼 것: `electron-builder.yml`, `.github/workflows/release.yml`, `src/main/auto-update.ts`.
  설치 파일에 서명이 없는데(unsigned) 자동 업데이트를 켜면 어떤 위험이 있는가.
  `latest.yml` 의 해시 무결성·업데이트 채널 가드가 있는가. 워크플로가 쓰는 권한이 필요한 최소인가.
  외부 액션이 태그가 아니라 커밋 SHA 로 고정돼 있는가.
- 문제 조건: 무결성 검증 없는 자동 업데이트 / 과한 워크플로 권한 / 태그만 믿는 액션 참조.

### L13. 컨테이너·클라우드 운영

- 쉬운 말: **남의 컴퓨터에서 돌 때 담장이 제대로 있는지** 본다.
- 볼 것: `deploy/` 의 docker-compose, cloudflared 터널, `pull-deploy.sh`, `smoke.sh`.
  컨테이너가 호스트 파일·네트워크에 얼마나 접근하는가(ADR-0010 의 경계 결정과 비교).
  종료할 때 진행 중 작업이 안전히 마무리되는가(ADR-0011 graceful drain).
- 문제 조건: 문서에 적힌 경계와 실제 설정 파일 불일치 / 비밀이 이미지·환경변수로 새는 경로.

### L14. 남의 코드 빌려 쓰기 (의존성·공급망)

- 쉬운 말: **빌려 쓴 부품이 낡거나 위험하지 않은지** 본다.
- 볼 것: `npm ls --depth=0` 으로 실제 의존 확인. 알려진 취약점(`npm audit` — **읽기만**).
  네이티브 모듈(node-pty) 이 없을 때 파이프 폴백이 정말 되는가, 그 경로에 테스트가 있는가.
  `engines.node` 범위가 실제 트리와 맞는가(`node scripts/engines-floor.mjs`). 라이선스 충돌은 없는가.
- 문제 조건: 안 쓰는데 남은 의존 / 폴백 경로가 테스트되지 않음 / 취약 패키지 상주.

### L15. 문서와 코드의 어긋남 (드리프트)

- 쉬운 말: **설명서와 실제 기계가 다른 곳**을 찾는다. 이 저장소는 문서가 많아 여기가 잘 어긋난다.
- 볼 것: `AGENTS.md`·`DESIGN.md`·`README.md` 의 **숫자·목록·파일 이름**을 실제와 대조
  (예: 승인 게이트 예외 모듈 개수, 배정 가능한 역할 목록, 기본 역량 표, `brain.md` 신선도).
- 확인 예: `npm run brain:check`, 문서에 나온 경로를 하나씩 `ls` 로 확인.
- 문제 조건: 산문에 박제된 값이 코드와 다름 → 그 자체가 나중에 잘못된 작업을 부른다.

### L16. 만드는 과정의 비용 (개발 프로세스 ROI)

- 쉬운 말: **숙제를 하기 전에 준비물 챙기는 데 시간이 더 걸리지 않는지** 본다.
- 볼 것: 게이트(`npm run verify`)가 한 번 도는 데 걸리는 시간, 규칙 문서의 양(`AGENTS.md`),
  스킬·훅·봇 리뷰 절차의 단계 수. 혼자 개발하는 사람이 **하루에 몇 번** 이 비용을 내는가.
- 문제 조건: 실제로 막아 준 사고보다 지불한 시간이 큰 절차 / 새 사람이 첫 PR 을 내기까지 읽어야 할 양이
  과도함. (반대로 "이건 비싸도 유지해야 한다"도 근거와 함께 적어라.)

### L17. 화면·접근성 (UI/UX)

- 쉬운 말: **눈이 잘 안 보이는 사람, 마우스를 못 쓰는 사람도 쓸 수 있는지** 본다.
- 볼 것: 색 대비, 키보드만으로 모든 기능에 닿을 수 있는가(`:focus-visible`), 화면 낭독기용 이름
  (aria-label), 움직임 줄이기 설정 존중(`prefers-reduced-motion`), 좁은 창·모바일 폭에서 깨지지 않는가.
- 문제 조건: 색으로만 상태를 표현 / 키보드로 못 여는 창 / **승인 창처럼 중요한 결정 화면**의 접근성 결함.

### L18. 말과 글 (다국어·문구)

- 쉬운 말: **한국어를 모르는 사람이 쓰면 어떻게 되는지** 본다.
- 볼 것: 화면 문구가 코드에 한국어로 박혀 있는가, 번역 구조가 있는가. 오류 문구가 사용자에게
  "무엇을 하라"를 알려주는가.
- 문제 조건: 국제화가 아예 불가능한 구조. (다만 지금 필요 없다면 "지금은 불필요"로 판정해도 좋다 — 규칙 5.)

### L19. 무슨 일이 있었는지 알 수 있는가 (관측성)

- 쉬운 말: **문제가 생겼을 때 CCTV가 있는지** 본다.
- 볼 것: 이벤트 로그(`FleetEvent`)가 남기는 정보로 사용자 버그를 재현할 수 있는가.
  로그 크기 제한·민감정보 가리기가 있는가. 사용자가 로그를 보내는 방법이 있는가.
- 문제 조건: 실패 원인 추적 불가 / 로그에 개인정보·키 포함.

### L20. 복잡도 핫스팟과 죽은 코드

- 쉬운 말: **너무 커서 아무도 못 건드리는 방**을 찾는다.
- 볼 것: `brain.md` 의 허브(연결이 많은 파일: `engine`, `server/boot` 등)와 긴 파일 상위 10개.
  순환 의존, 아무도 안 쓰는 export, 오래된 TODO/FIXME.
- 확인 예: 파일별 줄 수 정렬해 상위 15개 보기, `TODO`·`FIXME` 검색.
- 문제 조건: 한 파일이 여러 책임을 겸해 변경이 사방으로 번지는 구조 / 죽은 코드가 커버리지를 왜곡.

# 6. 진행 순서 (이 순서로 움직여라)

1. **지도 읽기**(1장) → 한 문단 요약을 먼저 내놓는다.
2. **기계 검사 먼저 돌리기**: `npm run typecheck`, `npm run lint`, `npm test`(또는 `npm run test:coverage`),
   `npm run brain:check`. 여기서 나오는 건 "확실한 사실"이라 제일 싸다.
3. **렌즈 순회**: L1~L20 을 순서대로. 렌즈마다 꼭 필요한 파일만 열고, 못 본 건 못 봤다고 적는다.
4. **반증 라운드**: 모아 둔 후보를 하나씩 깨보고, 살아남은 것만 남긴다.
5. **보고서 작성** → 파일로 저장 → 채팅에는 요약표와 상위 5개만.

시간이 모자라면 **L3·L4·L5·L6·L9·L11·L15 를 우선**한다(안전·계약·신뢰도 축).

| 말                    | 쉬운 뜻                                             |

## 부록 B. 짧은 버전 (빠르게 한 번만 볼 때)

> Fleet 저장소를 처음 보는 꼼꼼한 검사관으로서, `README.md` → `DESIGN.md` → `AGENTS.md` → `brain.md` →
> `docs/adr/` 순으로 읽고 `npm run typecheck`·`npm run lint`·`npm test` 를 돌린 뒤,
> ① 제품 약속 대비 실제 ② 아키텍처 경계 ③ 승인 게이트·비밀 관리 ④ 데스크톱/서버 두 표면의 짝 맞춤
> ⑤ 동시성·복구 ⑥ 오류·재시도 한도 ⑦ 테스트 신뢰도 ⑧ 배포·자동 업데이트 안전 ⑨ 의존성 ⑩ 문서 드리프트

> 표와 상세 카드로 보고해라. 코드는 고치지 말고 진단만 하고, 초등학생도 알아듣게 써라.
