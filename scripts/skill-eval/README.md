# 스킬 트리거 라우팅 측정

`.claude/skills/` 의 `description` 이 **의도한 쿼리에서 실제로 발동하는지**, 그리고
**엉뚱한 스킬을 켜거나 안 켜도 될 때 켜지는지**를 실측한다. description 은 스킬이 열릴지를
결정하는 유일한 장치라, 아무리 잘 쓴 본문도 여기서 미끄러지면 한 번도 실행되지 않는다.

## 왜 자체 하네스인가

skill-creator 의 `run_eval.py` 는 스킬 하나를 격리해 「발동/미발동」 이진 판정만 한다.
Fleet 은 7개 스킬이 서로 겹치는 표면(백로그 착수↔재랭킹, PR 리뷰↔갭 감사, 착수↔계획)을
가지므로 정작 알아야 할 것은 **어느 스킬이 켜졌나**다. 그래야 혼동 행렬이 나온다.
이 하네스는 모든 스킬이 살아있는 레포 트리에서 `claude -p` 를 돌리고 발동한 스킬 이름을
기록한다. 스킬이 열리는 즉시 프로세스 트리를 죽이고, 그전에도 프로브는 **일회용 사본**에서만
돈다(아래 「격리」) — 살아있는 체크아웃은 건드리지 않는다.

## 사용

```bash
# 전체 (31 쿼리 × 3런 = 93런, 10~20분)
node scripts/skill-eval/route-eval.mjs --out /tmp/iter1.jsonl
node scripts/skill-eval/report.mjs /tmp/iter1.jsonl

# 특정 쿼리만 빠르게
node scripts/skill-eval/route-eval.mjs --only pan-2,pr-3 --runs 1 --out /tmp/spot.jsonl
```

`verify` 에 넣지 않는다 — 실제 모델 호출이라 느리고 과금되며 런마다 흔들린다.
스킬을 **추가하거나 description 을 고칠 때** 손으로 돌리는 도구다.

주요 플래그: `--runs`(쿼리당 반복, 기본 3) · `--max-tools`(도구 **호출 건수** 예산, 기본 8) ·
`--timeout`(초, 기본 150) · `--workers`(동시 실행, 기본 8) · `--model` · `--no-isolate`.

### 격리 (기본 켜짐)

프로브가 스킬을 열지 않으면 예산·타임아웃까지 프롬프트를 **계속 실행한다**. negative 쿼리
`neg-2`·`neg-3` 은 파일을 고치라는 지시이고, claude 설정이 Edit/Bash 를 이미 허용해뒀다면
살아있는 체크아웃을 실제로 건드린다.

그래서 시작 시 작업 트리를 임시 템플릿으로 복사하고(`node_modules`·빌드 산출물 제외),
**작업마다 템플릿에서 새 사본을 떠서** 거기서 돌리고 끝나면 버린다. 사본 하나를 공유하면
파일을 고친 프로브의 변경과 git 인덱스를 뒤따르는 프로브가 보게 되어 결과가 스케줄링에
의존한다.

부수 효과로 **측정 중 레포를 편집해도 진행 중인 런이 오염되지 않는다** — 템플릿은 시작 시
한 번만 뜬다. before/after 를 연달아 돌릴 때 유용하다.

`.git` 은 보통 그대로 복사한다(프로브가 `git`·`gh` 로 레포 맥락을 조회하는 경로가 실사용과
같아야 한다). 다만 **linked worktree** 에서는 `.git` 이 원본 저장소 관리 디렉터리를 가리키는
포인터 *파일*이라, 복사하면 프로브의 `commit`·`tag` 가 **살아있는 저장소의 ref 를 실제로
변형**하고 temp 를 지워도 돌아오지 않는다. 그 경우 `.git` 을 빼고 빈 저장소를 새로 만든 뒤
origin 만 물린다(경고를 찍는다).

`--no-isolate` 는 이 보장을 전부 없앤다. 쓰지 마라.

### 원격·자격증명 격리

사본은 **로컬 파일만** 지킨다 — ref·GitHub 작업·자격증명은 지키지 못한다. 스킬이 안 열린
프로브는 프롬프트를 계속 수행하는데, `rel-3`("rc 로 먼저 태그 밀어보자")에서 `fleet-release`
가 미발동하면 에이전트가 문서대로 `git push origin v…` 를 실행할 수 있고, 그러면 **실제
태그가 올라가 `release.yml` 이 진짜 릴리스를 낸다.** immutable release 라 되돌릴 수도 없다.

두 겹으로 막는다.

- **origin 무력화** — origin 을 빈 bare 저장소로 갈아끼운다. 푸시가 갈 곳이 없다.
  **작업마다 따로** 둔다 — 하나를 공유하면 push 를 성사시킨 프로브의 ref 를 뒤따르는 프로브가
  fetch 로 보게 되어 결과가 다시 스케줄링에 의존한다.
- **환경 자격증명 제거** — `GH_TOKEN`·`GITHUB_TOKEN`·`SSH_AUTH_SOCK`·askpass 를 지우고,
  **`GIT_CONFIG_COUNT`/`_KEY_n`/`_VALUE_n` 주입**(git 인증을 실어나르는 경로)을 접두사로 지운다.
- **디스크 자격증명 차단** — 지우는 것만으로는 부족하다. `GH_CONFIG_DIR` 를 *지우면* `gh` 가
  `$HOME/.config/gh` 로 폴백해 로그인 상태를 되찾고, ssh 는 `-F` 로 설정을 끊어도 기본
  `~/.ssh/id_*` 를 계속 시도한다. 그러면 origin 을 무력화해도 `gh --repo owner/repo …` 나
  명시 URL 푸시로 살아있는 리소스를 건드릴 수 있다. 그래서 **빈 샌드박스로 가리킨다** —
  `GH_CONFIG_DIR`·`GIT_CONFIG_GLOBAL`·`GIT_CONFIG_SYSTEM` 을 빈 경로로 돌리고 ssh 는
  `IdentityAgent=none` + 빈 `-i`/`-F` 로 묶는다.

`HOME` 자체는 건드리지 않는다 — claude 의 인증·설정(`~/.claude`)이 거기 있어 옮기면 측정이
불가능해진다. 자격증명 표면만 골라 끊는다.

대가로 프로브의 `gh` 는 레포를 해석하지도 인증하지도 못한다. 측정 충실도를 조금 잃지만
라우팅 판정은 앞쪽 도구 호출 몇 개에서 끝나므로 영향이 작고(도구 호출 중앙값 1),
**반대 방향의 사고는 되돌릴 수 없다.**

### Windows 실행

`cross-spawn` 으로 띄운다. Windows 에서 npm 설치 CLI 는 `claude.cmd` 배치 셰임이라 node 의
`spawn` 으로는 PATHEXT 미해석 ENOENT, `.cmd` 명시는 Node 20+ 의 차단(CVE-2024-27980)으로
EINVAL 이 나 **프로브가 전부 실패한다**. 권위 설명은 `src/main/core/cli/detect.ts`.

### 프로브 환경

`CLAUDECODE` 와 **`CLAUDE_CODE_REMOTE`** 를 지우고 띄운다. 후자를 남기면
`.claude/hooks/session-start.mjs` 가 원격 부트스트랩 분기를 타고 프로브마다 `npm install` 을
동기 실행한다 — 사본에 node_modules 318MB 가 깔리고(실측), 그 시간이 라우팅 결과로
기록되며, 프롬프트와 무관하게 트리가 변형된다. 훅의 안내 문구 출력은 그 분기보다 앞이라
그대로 유지되므로 측정 조건은 실사용과 같다.

### 중단 처리

`SIGINT`·`SIGTERM`·미처리 예외에서 살아있는 프로브를 전부 죽이고 나간다. 없으면 10~20분짜리
명령을 Ctrl-C 한 뒤에도 유료 세션 여러 개가 계속 프롬프트를 실행한다.

스냅샷만 죽여서는 부족하다 — 죽은 자식의 `close` 로 워커가 다음 작업으로 넘어가 **교체
프로브를 새로 띄우고**, 그건 스냅샷에 없어 `process.exit` 후에도 살아남는다. `cancelled`
플래그를 먼저 세워 워커가 사본을 뜨거나 spawn 하지 못하게 막은 뒤, `live` 가 비고 그 상태가
유지되는 것을 확인하고 나간다.

### invalid 표본

`claude` 가 못 뜨거나 비정상 종료하면(인증 만료·잘못된 모델·레이트리밋) 그 표본은
`invalid` 로 찍히고 **모든 통계에서 제외**된다. 이걸 `none` 으로 기록하면 인프라 실패가
negative 정답이자 positive 미스로 둔갑해 그럴듯하지만 오염된 실험이 된다.
리포트가 건수와 사유를 맨 위에 낸다 — 0 이 아니면 숫자를 믿기 전에 원인부터 보라.

### 완결성 검증

`route-eval` 은 결과와 함께 `<out>.manifest.json`(계획된 쿼리·런 수·완료 시각)을 쓰고,
`report` 가 점수를 내기 **전에** 그것을 검증한다. 중간에 죽은 실행은 살아남은 앞부분 행만으로도
그럴듯한 100% 가 나오는데 그 안에는 스킬 하나가 통째로, 뒤쪽 negative 가 전부 빠져 있을 수
있다. 불완전하면 점수를 내지 않고 종료한다.

## 쿼리셋 (`queries.json`)

각 항목은 `{id, expected, query}` 이고 `expected` 는 켜져야 할 스킬 이름 또는 `none`.
`none` 쿼리는 **일부러 근접 오답**으로 골랐다 — 스킬과 키워드를 공유하지만 실제로는 다른
작업인 것들(`package.json 에 electron 몇 버전이야?` 는 "버전"을 말하지만 릴리스가 아니다).
명백히 무관한 쿼리는 아무것도 검증하지 못하므로 넣지 않는다.

스킬을 추가하면 positive 3~4개와 **그 스킬을 겨냥한 근접 오답** 1~2개를 함께 넣는다.

## 읽는 법

`--runs 3` 이라 쿼리당 0/3 ~ 3/3 이 나온다. 1/3·2/3 은 「가끔 켜진다」로, 고칠 대상이다.

세 가지를 구분해서 본다.

| 증상 | 의미 |
| --- | --- |
| `expected=X → none` | **미발동.** description 이 그 상황을 담지 못했다. |
| `expected=X → Y` | **혼동.** 두 description 의 경계가 겹친다. |
| `expected=none → X` | **과잉.** 근접 오답까지 빨아들인다. |

## 함정 — 도구 예산

모델이 스킬을 열기 전에 선행 작업(이슈 조회 등)을 먼저 하는 경우가 있다. 예산이 너무 작으면
**「6번째 호출에서 열었을 뿐인」 성공을 미발동으로 기록해 없는 회귀를 만들어낸다.**
실제로 겪었다 — 작은 예산에서 `fleet-backlog-induction` 이 92% → 67% 로 떨어져 보였으나
예산을 키워 수정 전후를 다시 재니 차이가 사라졌다. 회귀로 보고할 뻔했다.

**before/after 를 비교할 때는 반드시 같은 `--max-tools` 로 양쪽을 다시 재라.** 이전 런의
숫자를 그대로 가져다 비교하지 말 것.

예산은 **도구 호출 건수**(tool_use id 기준)로 센다. 초판은 도구 *이름*을 중복 제거해 셌고,
그래서 `WebFetch` 를 열 번 불러도 1 로 잡혀 예산이 사실상 무력했다(PR #337 Codex 리뷰에서
적발). 실측: `neg-3` 은 도구 이름이 `[Bash, Read]` 두 개뿐인데 실제 호출은 8건이다.
**그 수정 이전에 측정한 수치는 라벨보다 훨씬 큰 예산에서 나온 값이라 이후 값과 비교할 수 없다.**

리포트가 호출 건수의 중앙값·p90 을 함께 낸다. p90 이 `--max-tools` 에 붙어 있으면 예산이
포화된 것이니 키워서 다시 재라.

## 기준선 (2026-09, PR #337 · `--runs 3 --max-tools 12`)

`--runs 3 --max-tools 12 --workers 5`, 격리·자격증명 제거를 모두 적용한 상태:

| | 결과 |
| --- | --- |
| positive(발동해야) | **69/69 · 100%** — 7개 스킬 전부 |
| negative(안 켜야) | **24/24 · 오발동 0건** |
| 스킬 간 혼동 | **0건** |
| invalid | **0건** |

회귀를 볼 기준선이다. description 을 고치거나 스킬을 추가한 뒤 이보다 떨어지면 그 변경을
의심하라.

> ⚠ **디스크 자격증명 격리(`GH_CONFIG_DIR`·git 전역설정·ssh 기본키 차단) 도입 전** 값이다.
> 그 변경으로 프로브의 `gh`·`git` 인증 표면이 또 달라졌으므로 재측정 중이다.

**동시성을 올리면 invalid 가 난다.** `--workers 8` 로 몰아친 이전 실행에서는 후반 negative
9건이 `exit=1` 로 죽었다(즉사 또는 작업 중간 사망, stderr 없음). 같은 쿼리를 `--workers 4`
로 다시 돌리니 12/12 정상이라 스로틀로 판정했고, `--workers 5` 로 낮춘 위 실행은 invalid 가
0 이다. **invalid 표식이 없었다면 그 9건이 조용히 「negative 정답」으로 집계돼 점수를
부풀렸을 것이다.** invalid 가 뜨면 동시성을 낮춰 다시 재라 — 그 숫자를 그대로 쓰지 마라.

## 이 하네스가 처음 낸 결과는 틀렸다 — 그 경위

PR #337 은 원래 「`fleet-plan-panel` 이 56%, `fleet-pr-review` 가 67% 로 미발동하니
description 을 고쳤다」는 내용이었다. **그 미발동은 존재하지 않았다.** 위 예산 계수 버그가
만들어낸 허상이었고, 교정 후 같은 description 을 다시 재니 처음부터 69/69 였다.
Codex 리뷰가 계수 버그를 짚지 않았으면 없는 문제를 고친 PR 이 머지될 뻔했다.

같은 뿌리에서 나온 오판이 둘 더 있었다 — 「`fleet-backlog-induction` 이 92%→67% 로 회귀」
(예산을 바꾸자 사라짐), 「`이슈 N 확인하고 착수해` 가 35% 만 연다」(교정 후 12/12).

남길 교훈은 description 작성법이 아니라 **측정 자체의 규율**이다.

- **도구가 재는 값이 라벨과 같은지 먼저 의심하라.** 「예산 5 vs 12 에서 결과가 다르다」를
  발견했을 때가 하네스를 의심할 지점이었는데, 예산 *값*만 바꿔보고 *계수 방식*은 들여다보지
  않았다. 이상한 수치의 첫 용의자는 피측정물이 아니라 측정기다.
- **n=5 로 판단하지 마라.** induction 에서 1/5 → 3/5 로 개선처럼 보인 구간이 있었으나
  20런으로 늘리자 7/20 → 7/20 으로 사라졌다. 거기서 멈췄다면 없는 개선을 실었을 것이다.
- **효과가 측정되지 않는 변경은 싣지 마라.** 이 PR 의 description 변경 2건은 그래서
  되돌렸다 — 「더 나아 보이는 문장」은 근거가 아니다.
- **before/after 는 같은 설정으로 양쪽을 *다시* 재라.** 이전 런의 숫자를 가져다 쓰면
  하네스가 그 사이 바뀌었을 때 조용히 틀린다.

기존 description 이 전부 100% 였으므로 **description 작성법에 대해 이 레포가 실측으로
말할 수 있는 것은 아직 없다.** 실패 사례가 나오면 그때 여기 적는다.
