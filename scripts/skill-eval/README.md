# 스킬 트리거 라우팅 측정

`.claude/skills/` 의 `description` 이 **의도한 쿼리에서 실제로 발동하는지**, 그리고
**엉뚱한 스킬을 켜거나 안 켜도 될 때 켜지는지**를 실측한다. description 은 스킬이 열릴지를
결정하는 유일한 장치라, 아무리 잘 쓴 본문도 여기서 미끄러지면 한 번도 실행되지 않는다.

## 왜 자체 하네스인가

skill-creator 의 `run_eval.py` 는 스킬 하나를 격리해 「발동/미발동」 이진 판정만 한다.
Fleet 은 7개 스킬이 서로 겹치는 표면(백로그 착수↔재랭킹, PR 리뷰↔갭 감사, 착수↔계획)을
가지므로 정작 알아야 할 것은 **어느 스킬이 켜졌나**다. 그래야 혼동 행렬이 나온다.
이 하네스는 모든 스킬이 살아있는 레포 트리에서 `claude -p` 를 돌리고 발동한 스킬 이름을
기록한다. 스킬이 열리는 즉시 프로세스 트리를 죽이고, 그전에도 프로브는 **일회용 사본**에서만
돈다(아래 「격리」) — 살아있는 체크아웃은 건드리지 않는다.

## 사용

```bash
# 전체 (31 쿼리 × 3런 = 93런, 10~20분)
node scripts/skill-eval/route-eval.mjs --out /tmp/iter1.jsonl
node scripts/skill-eval/report.mjs /tmp/iter1.jsonl

# 특정 쿼리만 빠르게
node scripts/skill-eval/route-eval.mjs --only pan-2,pr-3 --runs 1 --out /tmp/spot.jsonl
```

`verify` 에 넣지 않는다 — 실제 모델 호출이라 느리고 과금되며 런마다 흔들린다.
스킬을 **추가하거나 description 을 고칠 때** 손으로 돌리는 도구다.

주요 플래그: `--runs`(쿼리당 반복, 기본 3) · `--max-tools`(도구 **호출 건수** 예산, 기본 8) ·
`--timeout`(초, 기본 150) · `--workers`(동시 실행, 기본 8) · `--model` · `--no-isolate`.

### 격리 (기본 켜짐)

프로브가 스킬을 열지 않으면 예산·타임아웃까지 프롬프트를 **계속 실행한다**. negative 쿼리
`neg-2`·`neg-3` 은 파일을 고치라는 지시이고, claude 설정이 Edit/Bash 를 이미 허용해뒀다면
살아있는 체크아웃을 실제로 건드린다. 그래서 시작 시 작업 트리를 임시 디렉터리로 복사해
거기서 돌리고 끝나면 통째로 버린다(`node_modules`·빌드 산출물 제외, `.git` 은 포함 —
프로브가 `git`·`gh` 로 레포 맥락을 조회하는 경로가 실사용과 같아야 한다).

부수 효과로 **측정 중 레포를 편집해도 진행 중인 런이 오염되지 않는다** — 사본은 시작 시
한 번만 뜬다. before/after 를 연달아 돌릴 때 유용하다.

`--no-isolate` 는 이 보장을 없앤다. 쓰지 마라.

### invalid 표본

`claude` 가 못 뜨거나 비정상 종료하면(인증 만료·잘못된 모델·레이트리밋) 그 표본은
`invalid` 로 찍히고 **모든 통계에서 제외**된다. 이걸 `none` 으로 기록하면 인프라 실패가
negative 정답이자 positive 미스로 둔갑해 그럴듯하지만 오염된 실험이 된다.
리포트가 건수와 사유를 맨 위에 낸다 — 0 이 아니면 숫자를 믿기 전에 원인부터 보라.

## 쿼리셋 (`queries.json`)

각 항목은 `{id, expected, query}` 이고 `expected` 는 켜져야 할 스킬 이름 또는 `none`.
`none` 쿼리는 **일부러 근접 오답**으로 골랐다 — 스킬과 키워드를 공유하지만 실제로는 다른
작업인 것들(`package.json 에 electron 몇 버전이야?` 는 "버전"을 말하지만 릴리스가 아니다).
명백히 무관한 쿼리는 아무것도 검증하지 못하므로 넣지 않는다.

스킬을 추가하면 positive 3~4개와 **그 스킬을 겨냥한 근접 오답** 1~2개를 함께 넣는다.

## 읽는 법

`--runs 3` 이라 쿼리당 0/3 ~ 3/3 이 나온다. 1/3·2/3 은 「가끔 켜진다」로, 고칠 대상이다.

세 가지를 구분해서 본다.

| 증상 | 의미 |
| --- | --- |
| `expected=X → none` | **미발동.** description 이 그 상황을 담지 못했다. |
| `expected=X → Y` | **혼동.** 두 description 의 경계가 겹친다. |
| `expected=none → X` | **과잉.** 근접 오답까지 빨아들인다. |

## 함정 — 도구 예산

모델이 스킬을 열기 전에 선행 작업(이슈 조회 등)을 먼저 하는 경우가 있다. 예산이 너무 작으면
**「6번째 호출에서 열었을 뿐인」 성공을 미발동으로 기록해 없는 회귀를 만들어낸다.**
실제로 겪었다 — 작은 예산에서 `fleet-backlog-induction` 이 92% → 67% 로 떨어져 보였으나
예산을 키워 수정 전후를 다시 재니 차이가 사라졌다. 회귀로 보고할 뻔했다.

**before/after 를 비교할 때는 반드시 같은 `--max-tools` 로 양쪽을 다시 재라.** 이전 런의
숫자를 그대로 가져다 비교하지 말 것.

예산은 **도구 호출 건수**(tool_use id 기준)로 센다. 초판은 도구 *이름*을 중복 제거해 셌고,
그래서 `WebFetch` 를 열 번 불러도 1 로 잡혀 예산이 사실상 무력했다(PR #337 Codex 리뷰에서
적발). 실측: `neg-3` 은 도구 이름이 `[Bash, Read]` 두 개뿐인데 실제 호출은 8건이다.
**그 수정 이전에 측정한 수치는 라벨보다 훨씬 큰 예산에서 나온 값이라 이후 값과 비교할 수 없다.**

리포트가 호출 건수의 중앙값·p90 을 함께 낸다. p90 이 `--max-tools` 에 붙어 있으면 예산이
포화된 것이니 키워서 다시 재라.

## 기준선 (2026-09, PR #337 · `--runs 3 --max-tools 12`)

| | positive | negative(오발동) | 전체 |
| --- | --- | --- | --- |
| 7개 스킬 현행 description | **69/69 100%** | 0/24 | **93/93 100%** |

스킬 간 혼동 0건. 회귀를 볼 기준선이므로 description 을 고치거나 스킬을 추가한 뒤 이보다
떨어지면 그 변경을 의심하라.

## 이 하네스가 처음 낸 결과는 틀렸다 — 그 경위

PR #337 은 원래 「`fleet-plan-panel` 이 56%, `fleet-pr-review` 가 67% 로 미발동하니
description 을 고쳤다」는 내용이었다. **그 미발동은 존재하지 않았다.** 위 예산 계수 버그가
만들어낸 허상이었고, 교정 후 같은 description 을 다시 재니 처음부터 69/69 였다.
Codex 리뷰가 계수 버그를 짚지 않았으면 없는 문제를 고친 PR 이 머지될 뻔했다.

같은 뿌리에서 나온 오판이 둘 더 있었다 — 「`fleet-backlog-induction` 이 92%→67% 로 회귀」
(예산을 바꾸자 사라짐), 「`이슈 N 확인하고 착수해` 가 35% 만 연다」(교정 후 12/12).

남길 교훈은 description 작성법이 아니라 **측정 자체의 규율**이다.

- **도구가 재는 값이 라벨과 같은지 먼저 의심하라.** 「예산 5 vs 12 에서 결과가 다르다」를
  발견했을 때가 하네스를 의심할 지점이었는데, 예산 *값*만 바꿔보고 *계수 방식*은 들여다보지
  않았다. 이상한 수치의 첫 용의자는 피측정물이 아니라 측정기다.
- **n=5 로 판단하지 마라.** induction 에서 1/5 → 3/5 로 개선처럼 보인 구간이 있었으나
  20런으로 늘리자 7/20 → 7/20 으로 사라졌다. 거기서 멈췄다면 없는 개선을 실었을 것이다.
- **효과가 측정되지 않는 변경은 싣지 마라.** 이 PR 의 description 변경 2건은 그래서
  되돌렸다 — 「더 나아 보이는 문장」은 근거가 아니다.
- **before/after 는 같은 설정으로 양쪽을 *다시* 재라.** 이전 런의 숫자를 가져다 쓰면
  하네스가 그 사이 바뀌었을 때 조용히 틀린다.

기존 description 이 전부 100% 였으므로 **description 작성법에 대해 이 레포가 실측으로
말할 수 있는 것은 아직 없다.** 실패 사례가 나오면 그때 여기 적는다.
