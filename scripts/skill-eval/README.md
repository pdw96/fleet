# 스킬 트리거 라우팅 측정

`.claude/skills/` 의 `description` 이 **의도한 쿼리에서 실제로 발동하는지**, 그리고
**엉뚱한 스킬을 켜거나 안 켜도 될 때 켜지는지**를 실측한다. description 은 스킬이 열릴지를
결정하는 유일한 장치라, 아무리 잘 쓴 본문도 여기서 미끄러지면 한 번도 실행되지 않는다.

## 왜 자체 하네스인가

skill-creator 의 `run_eval.py` 는 스킬 하나를 격리해 「발동/미발동」 이진 판정만 한다.
Fleet 은 7개 스킬이 서로 겹치는 표면(백로그 착수↔재랭킹, PR 리뷰↔갭 감사, 착수↔계획)을
가지므로 정작 알아야 할 것은 **어느 스킬이 켜졌나**다. 그래야 혼동 행렬이 나온다.
이 하네스는 모든 스킬이 살아있는 실제 레포에서 `claude -p` 를 돌리고 발동한 스킬 이름을
기록한다. 스킬이 열리는 즉시 프로세스 그룹을 죽이므로 **실제 작업은 수행되지 않는다**.

## 사용

```bash
# 전체 (31 쿼리 × 3런 = 93런, 10~20분)
node scripts/skill-eval/route-eval.mjs --out /tmp/iter1.jsonl
node scripts/skill-eval/report.mjs /tmp/iter1.jsonl

# 특정 쿼리만 빠르게
node scripts/skill-eval/route-eval.mjs --only pan-2,pr-3 --runs 1 --out /tmp/spot.jsonl
```

`verify` 에 넣지 않는다 — 실제 모델 호출이라 느리고 과금되며 런마다 흔들린다.
스킬을 **추가하거나 description 을 고칠 때** 손으로 돌리는 도구다.

주요 플래그: `--runs`(쿼리당 반복, 기본 3) · `--max-tools`(도구 예산, 기본 8) ·
`--timeout`(초, 기본 150) · `--workers`(동시 실행, 기본 8) · `--model`.

## 쿼리셋 (`queries.json`)

각 항목은 `{id, expected, query}` 이고 `expected` 는 켜져야 할 스킬 이름 또는 `none`.
`none` 쿼리는 **일부러 근접 오답**으로 골랐다 — 스킬과 키워드를 공유하지만 실제로는 다른
작업인 것들(`package.json 에 electron 몇 버전이야?` 는 "버전"을 말하지만 릴리스가 아니다).
명백히 무관한 쿼리는 아무것도 검증하지 못하므로 넣지 않는다.

스킬을 추가하면 positive 3~4개와 **그 스킬을 겨냥한 근접 오답** 1~2개를 함께 넣는다.

## 읽는 법

`--runs 3` 이라 쿼리당 0/3 ~ 3/3 이 나온다. 1/3·2/3 은 「가끔 켜진다」로, 고칠 대상이다.

세 가지를 구분해서 본다.

| 증상 | 의미 |
| --- | --- |
| `expected=X → none` | **미발동.** description 이 그 상황을 담지 못했다. |
| `expected=X → Y` | **혼동.** 두 description 의 경계가 겹친다. |
| `expected=none → X` | **과잉.** 근접 오답까지 빨아들인다. |

## 함정 — 도구 예산

모델이 스킬을 열기 전에 선행 작업(이슈 조회 등)을 먼저 하는 경우가 있다. 예산이 너무 작으면
**「6번째 도구에서 열었을 뿐인」 성공을 미발동으로 기록해 없는 회귀를 만들어낸다.**
실제로 겪었다 — 예산 5에서 `fleet-backlog-induction` 이 92%→67% 로 떨어져 보였으나,
예산 12로 수정 전후를 다시 재니 75% vs 83% 로 차이가 사라졌다. **before/after 를 비교할
때는 반드시 같은 `--max-tools` 로 양쪽을 다시 재라.** 이전 런의 숫자를 그대로 가져다
비교하지 말 것.

## 실측에서 나온 교훈 (2026-09, PR #337)

- **공격적으로 쓴다고 오발동이 늘지 않았다.** `fleet-release` 는 발화 예시를 6개 나열하고
  "사용자가 '스킬'이라 말하지 않아도 … 적극 사용한다"까지 적었는데 100% 발동에 근접
  오답 오발동 0건이었다. 나머지 스킬을 그 형태로 맞췄고 정밀도는 그대로였다.
- **키워드가 들어있다고 켜지지 않는다.** `fleet-pr-review` 에는 `"스펙/변경 독립 검증" 시
  사용` 이 문자 그대로 있었는데도 해당 쿼리가 0/3 이었다. 앞 절의 "Codex 한도 소진 시
  대체·PR 전 자가리뷰용"이 **용도가 아니라 발동 전제조건**으로 읽힌 탓이다.
- **의식(儀式)의 이름이 아니라 상황을 적어라.** `fleet-plan-panel` 의 발동 예시는 둘 다
  "패널"이라는 단어를 사용자가 먼저 말해야 했다. 본문 「언제」가 규정한 실제 조건(승인된
  스펙 + 구현 계획 필요)을 description 으로 올리자 56%→100% 가 됐다.
- **"~면 생략" 류 단서는 면허로 읽힌다.** `소형 작업은 패널 생략(적응형)` 이 description
  끝에 있으니 안 켜도 된다는 뜻이 됐다. 그런 판정은 스킬 본문으로 내려야 한다.

## 알려진 약점 — `ind-2` (미해결)

`이슈 31 확인하고 착수해` 는 `fleet-backlog-induction` 을 **20런 중 7런(35%)** 만 연다.
description 에 `"이슈 27 확인하고 작업 진행" 류 지시 시 사용` 이 이미 문자 그대로 있는데도
그렇다. 실패 런의 도구 흔적은 늘 같다 — `Bash → Read → ToolSearch → WebFetch`, 즉
**이슈를 조회하러 갔다가 스킬로 돌아오지 않는다**.

description 수정을 시도했고 **측정 결과 효과가 없어 되돌렸다**: 「이슈 본문 조회는 1단계
(선정)이지 작업 자체가 아니다 — 조회로 끝내지 말고 이 스킬을 열라」는 문장을 넣었더니
수정 전 7/20, 수정 후 7/20 으로 **완전히 동일**했다(중간에 1/5 → 3/5 로 좋아 보인 구간이
있었으나 표본을 20으로 늘리자 사라졌다 — n=5 로는 판단하지 말 것).

남은 가설 둘, 둘 다 미검증:

1. 쿼리가 조회를 **명시적으로 먼저 지시**하므로(「확인하고」) 모델이 그에 복종하는 것이
   맞는 행동이고, description 으로 뒤집을 수 있는 종류가 아니다. 같은 스킬의 `ind-1`
   (`#27 에서 다음 거 골라서…`)은 20/20 으로 완벽한데, 그쪽은 조회를 지시하지 않는다.
2. 측정 환경 artifact — 샌드박스에서 이슈 조회가 헛돌면서(`ToolSearch`·`WebFetch` 로
   GitHub 도구를 찾아 헤맨다) 도구 예산을 소진한다. 실사용 환경에서는 덜할 수 있다.

가설 2가 맞다면 `--max-tools` 를 크게 주고 재면 구분된다. 손대기 전에 그것부터 하라.
